# 本地持久化与云端同步

这套项目的数据层不是「有网走云、没网报错」，而是**本地优先（local-first）**：
所有数据先落到本机，界面永远只读本地，云数据库只负责备份与多端同步。

结果就是：**没网、没开云环境、云函数报错，界面功能一样完整可用。**

---

## 一、整体结构

```
页面（pages/*）
   ↓ 只调这一层
biz.js          业务动作：建档、充值、核销、统计…（永远返回结果，不抛错）
   ↓
store.js        本地存储：读写、软删除、发件箱、冲突合并
sync.js         云同步：推送、拉取、探测环境、失败降级
   ↓
微信本地存储 (wx.setStorageSync)  ←→  云数据库（可选）
```

三个文件都在 `miniapp/utils/`：

| 文件 | 职责 | 会不会抛错 |
|---|---|---|
| `store.js` | 纯本地读写，不碰网络 | 不抛，失败返回 false / 空数组 |
| `sync.js` | 云调用，失败自动降级 | 不抛，返回 `{ ok: false, degraded: true }` |
| `biz.js` | 业务规则、金额计算、格式化 | 不抛，返回 `{ ok: false, msg }` |

**页面永远不需要 try/catch。** 这是刻意的设计——收银场景断网是常态，不能因为网络问题让店员点不动按钮。

## 二、本地存储设计

### 2.1 存储键

```
qy:coll:members       会员
qy:coll:records       流水
qy:coll:memberCards   会员次卡
qy:coll:levels        等级
qy:coll:cardTypes     次卡项目
qy:coll:services      服务项
qy:coll:config        门店配置
qy:meta               同步元信息
qy:outbox             待同步操作队列
```

一个集合一个键，`wx.getStorageSync` 一次拿全量。单店数据量（几千条）完全放得下——微信本地存储上限 10MB，一张会员记录约 300 字节，够放三万多条。

### 2.2 每条记录带四个同步元字段

```js
{
  _id: 'm-chenjiayi',
  name: '陈嘉怡',
  balance: 128000,

  // 下面四个是同步用的
  updatedAt: 1732626000000,  // 最后修改时间（毫秒）
  rev: 3,                    // 修改版本号
  _deleted: false,           // 软删除标记
  _dirty: false              // 本地改过但还没推上云
}
```

- `updatedAt` + `rev` 解决冲突（见第四节）
- `_deleted` 而不是真删：真删掉的话，另一台设备拉数据时**收不到「这条被删了」的信号**，会一直显示着
- `_dirty` 标记哪些记录还没推上去，避免推送成功前被云端旧数据覆盖

### 2.3 金额一律存「分」

```js
balance: 128000   // 实际是 1280.00 元
```

理由很简单：`0.1 + 0.2 !== 0.3` 在浮点数里是常识，收银系统用浮点存钱迟早出事。展示时才除以 100。

`biz.js` 提供三个转换函数：

```js
biz.money(128000)      // "1,280.00"  带千分位
biz.moneyShort(128000) // "1,280"     卡片大数字
biz.toFen('128.00')    // 12800       输入框转回来
```

## 三、同步逻辑

### 3.1 三个触发时机

| 时机 | 触发方式 | 说明 |
|---|---|---|
| 启动 | `app.js` 里延迟 600ms 调一次 | 不抢首屏渲染 |
| 页面显示 | `biz.refresh()` | 60 秒节流，不会每次切页都打云函数 |
| 手动 | 设置页「立即同步」 | 用户主动重试 |
| 网络恢复 | `wx.onNetworkStatusChange` | 断网期间攒的操作立刻补推 |
| 数据变更后 | 各页面写操作后调 `biz.syncNow()` | 先落本地，再异步推 |

### 3.2 先推后拉，顺序不能反

```js
const pushRes = await push()   // 先把本地修改推上去
const pullRes = await pull()   // 再拉云端变更
```

反过来做的话，本地还没推的修改会被判定成「和云端冲突」，白白多一轮合并。

### 3.3 发件箱（outbox）

每次写操作往 `qy:outbox` 里塞一条：

```js
{ coll: 'members', op: 'upsert', id: 'm-xxx', doc: {...}, ts: 1732626000000 }
```

**关键优化：同一条记录的连续修改会合并。** 店员连改 5 次备注，发件箱里只留最后一次，补推时不会做 5 次无用同步。

推送时逐条走，**某一条失败就停下**——因为后面的操作可能依赖前一条（先建会员，再给会员充值）。已经成功的部分出队，剩余的留到下次。

### 3.4 增量拉取

```js
// 只拉比上次同步时间新的记录
const since = store.getMeta().lastSyncAt || 0
await callCloud('sync', { action: 'pull', coll, since })
```

游标用**服务端返回的时间**，不是本地时间。本地时钟慢 5 分钟的机器，用本地时间做游标会漏拉数据。

### 3.5 单次上限 100 条

云函数 `pull` 每次最多返回 100 条，返回 `hasMore` 标记。数据多时会分多次拉完，避免一次查询超时。

## 四、冲突解决：Last Write Wins

同一份数据被两台设备改过，怎么办？

```js
// store.js mergeRemote
if (cur._dirty) continue                     // 本地有未推的修改，先不覆盖

const remoteNewer =
  r.updatedAt > cur.updatedAt ||
  (r.updatedAt === cur.updatedAt && r.rev > cur.rev)

if (remoteNewer) 用云端覆盖本地
```

规则很朴素：

1. **本地有未推送的修改** → 保留本地，等推送时覆盖云端
2. **云端更新** → 覆盖本地
3. **时间相同** → 比 `rev`，大的赢

为什么不用字段级合并：**余额这种数字没法「合并」**。A 机器算出 1000，B 机器算出 900，合并成 950 是错的，只能认一个。LWW 简单、可预测，单店多人操作够用。

代价要说清楚：**两台设备同时改同一个会员的余额，后写的赢，前一次会丢。** 要彻底避免，得在云函数里用数据库事务 + `_.inc()` 原子操作（见 [CLOUD.md](CLOUD.md) 第 9 节）。当前这套本地优先的实现适合「一人一台机、偶尔断网补同步」的场景，不适合多人同时改同一个会员。

## 五、降级机制

### 5.1 三级探测

`sync.probe()` 判断云开发能不能用，三个条件缺一不可：

```js
1. wx.cloud 存在            // 基础库够新
2. app.js 配了 env          // 不是空串、不是占位符
3. wx.cloud.init 没抛异常
```

任何一条不满足 → `available = false` → 全程本地模式，**不报错、不弹窗、不影响界面**。

### 5.2 失败即降级，不是失败即报错

```js
function degrade(e) {
  state.available = false
  state.lastError = e.message
  store.setMeta({ mode: 'local' })
  return { ok: false, degraded: true, msg: state.lastError }
}
```

云函数超时（8 秒）、断网、报错，都走这条路径。界面只在设置页显示一个灰色的「本地存储」状态，不打断用户。

### 5.3 界面上的表现

| 场景 | 设置页显示 | 用户感知 |
|---|---|---|
| 配了 env 且能连 | 已连接云端 · 绿点 | 无感 |
| 没配 env | 本地存储 · 灰点 | 看到「数据保存在本机」 |
| 断网 | 离线中 · 黄点 | 提示「联网后自动补同步」 |
| 云函数报错 | 云端不可用 · 黄点 + 具体原因 | 数据照常保存 |

首页底部那行小字也会跟着变：`已同步云端 · 11-27 08:32` / `数据保存在本机` / `当前离线，数据已存本机` / `3 项待同步`。点它可以手动重试。

## 六、页面怎么用

只有三个调用点：

### 6.1 页面显示时

```js
onShow() {
  this.setData({ theme: app.globalData.theme })
  this.loadData()      // 读本地，立即有数据
  biz.refresh()        // 后台尝试同步，60 秒节流
}
```

### 6.2 读数据

```js
const list = biz.listMembers({ keyword: '陈' }).map(biz.memberRow)
```

`biz.memberRow()` 把原始记录转成**列表页可以直接渲染的扁平结构**（含格式化后的字符串、头像配色类名），WXML 里不用写任何计算。

### 6.3 写数据

```js
const r = biz.recharge(memberId, 50000)
if (!r.ok) { wx.showToast({ title: r.msg }); return }

biz.syncNow().catch(() => {})   // 后台推云，失败也不管
```

写操作**先落本地、立即返回**，推送是异步的。断网时 `.catch()` 吃掉错误，数据已经在本地了。

## 八、接入云开发

三步：

1. 在 `miniapp/app.js` 的 `globalData.env` 填云环境 ID
2. 云开发控制台建 7 个集合（字段见 [CLOUD.md](CLOUD.md) 第 3 步）
3. 上传部署 `miniapp/cloudfunctions/sync`

填好 env 后重启小程序，设置页会从「本地存储」变成「已连接云端」。

**没配 env 也能正常用**——这是这套设计最重要的性质，也是它能直接给别人试用的原因。

## 九、已知限制

诚实列出：

- **多人同时改同一个会员会丢更新**。LWW 只保证最终一致，不保证不丢。要严格，必须走云函数事务。
- **本地存储 10MB 上限**。单店三万多条记录没问题，做连锁会撑不住，需要改造分页加载。
- **换手机数据不带走**。除非开了云同步。《CLOUD.md》里有迁移方案。
- **没有加密**。微信本地存储是明文的，手机被 root 后可读。要存敏感信息得自己加一层。
- **`_deleted` 记录不会自动清理**。长期运行会累积，可加个定时任务真删 30 天前的已删记录。
