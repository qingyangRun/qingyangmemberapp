# 路线图

当前进度：**界面 + 数据层完成，云端待实际部署。**

- 界面：14 屏全部完成，原生小程序可直接编译
- 数据层：本地持久化 + 云端同步 + 自动降级，14 个页面全部接真实数据
- 云端：云函数代码已写好，但需要使用者自己开环境、建集合、上传部署

---

## 阶段一：界面与原型 ✅

- [x] 14 屏界面设计（375×812，微信小程序画幅）
- [x] 静态 HTML 原型，页面互相链接，点得动
- [x] 设计变量体系 `tokens.css`
- [x] 6 套主题色（经典蓝 / 清样绿 / 雅紫 / 琥珀橙 / 玫瑰红 / 石墨黑）

- [x] 自定义底部标签栏（工作台 / 会员 / 记录 / 数据 / 管理）

## 阶段二：数据层 ✅

- [x] 本地持久化存储（`store.js`）
  - 7 个集合分键存储
  - 软删除（`_deleted`），保证多端能收到删除信号
  - 发件箱（outbox），同一记录连续修改自动合并
  - Last Write Wins 冲突合并
- [x] 云端同步（`sync.js` + `cloudfunctions/sync`）
  - 先推后拉，避免误判冲突
  - 增量拉取，服务端时间做游标
  - 三级环境探测，任一不满足即降级
  - 8 秒超时、网络恢复自动补同步
- [x] 业务逻辑层（`biz.js`）
  - 建档 / 编辑 / 充值 / 购卡 / 核销 / 统计全部真实运算
  - 金额统一以「分」为单位存整数
  - 所有方法不抛错，返回 `{ ok, msg }`
- [x] 14 个页面全部接真实数据
- [x] 自测脚本 `__smoke.js`，55 项断言全通过
- [x] 云不可用降级：断网、没配 env、云函数报错，功能全部正常

## 阶段三：云端实际部署（使用者操作）

代码已就绪，需要使用者按 [CLOUD.md](CLOUD.md) 操作：

- [ ] 开通云开发环境，拿到环境 ID
- [ ] 在 `app.js` 的 `globalData.env` 填入
- [ ] 建 7 个集合（`members` / `levels` / `cardTypes` / `memberCards` / `records` / `services` / `config`）
- [ ] 建索引（`phone`、`cardNo` 唯一索引最关键）
- [ ] 配集合权限（金额相关集合设为「仅管理端可读写」）
- [ ] 上传部署 `cloudfunctions/sync`

## 阶段四：账号与权限

- [ ] 微信登录（`wx.login` → `openid`）
- [ ] 角色：店主 / 店长 / 员工
- [ ] 员工权限：能否改价、能否送赠、能否删除记录
- [ ] 操作日志（谁在什么时候做了什么）

## 阶段五：并发与一致性

当前已知短板，优先级最高的技术债：

- [ ] **核销、充值走云函数事务**，用 `_.inc()` 原子操作替代「先读再算再写」
  - 现状：多台设备同时改同一会员余额会丢更新（LWW 只保证最终一致）
  - 目标：金额操作原子化，并发下不丢
- [ ] 流水只追加、禁止修改删除（云函数层面强制）
- [ ] 云函数按职责拆分（现在统一在 `sync`，可按 `CLOUD.md` 里那 7 个函数拆）

## 不做

以下功能明确不在本项目范围，避免变成又一个重型 SaaS：

- 复杂的营销裂变（分销、拼团、砍价）
- 商品商城与物流
- 财务对账与发票
- 多租户 SaaS 平台化

保持「一家小店够用的会员系统」这个定位。
